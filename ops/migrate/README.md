# Перенос приюта со старого сайта в новый проект

`migrate.sh` переносит **один** приют из базы старого сайта (несколько приютов, ветка `main`) в **новый пустой** проект Supabase со схемой одного приюта (`supabase/migrations/20261113000000_single_shelter.sql`).

Без `--apply` скрипт только показывает план и ничего не меняет. С `--apply` он одной транзакцией копирует приют, его волонтёров вместе с входом (почта, хэш пароля, второй фактор), животных, вольеры, проекты, нужды, журнал закупок и галерею, затем фото, затем сверяет цель с источником. При любом расхождении выводит `FAIL` и завершается с ошибкой.

## Что нужно

`psql`, `gpg`, `curl`, `python3`, Docker и Supabase CLI (как для `ops/backup/restore-drill.sh`).

## Порядок

1. Создайте новый проект Supabase `live-life` (регион Франкфурт). В Authentication → Sign In / Providers → Multi-Factor включите TOTP (на бесплатном тарифе он включён по умолчанию; проверьте).
2. Примените схему к новому проекту: `supabase link --project-ref <новый>` и `supabase db push` из ветки `astro`. Только к **новому** проекту.
3. Пробный запуск из ночной копии (`ops/backup`):

   ```bash
   export TARGET_DB_URL='Session pooler нового проекта'
   export TARGET_URL='https://<новый>.supabase.co'
   export TARGET_SERVICE_KEY='service_role ключ нового проекта'
   export BACKUP_PASSPHRASE='пароль копий'
   ops/migrate/migrate.sh --slug live-life --backup db/2026-11-13.tar.gz.gpg --photos photos
   ```

   Копия восстанавливается через `ops/backup/restore.sh` во временный локальный Supabase (порты 55320–55329), который удаляется в конце. Живая база не читается вовсе.

   **Перед запуском остановите локальную базу для просмотра сайта**, если она работает: она занимает те же порты 55320–55329. В папке `~/shelter-astro`: `npx -y supabase@2.122.0 stop` (данные просмотра сохранятся, запустить снова — `npx -y supabase@2.122.0 start`).
4. Проверьте план и запустите то же с `--apply`. В конце должно быть `MIGRATION CHECK PASSED`.

Вместо копии можно указать уже восстановленную старую базу: `SOURCE_DB_URL` и `SOURCE_URL` без `--backup`. Источник только читается.

## Что переносится и как

- Пользователи входа — только волонтёры этого приюта, с теми же id, почтой, хэшем пароля и секретом TOTP: волонтёры входят со старым паролем и тем же приложением-аутентификатором. Сессии не переносятся, войти нужно заново.
- Адреса фото животных переписываются на новый проект; пути файлов в хранилище не меняются.
- Даты (создание, смена статуса, завершение проекта, отметка «нужна помощь с лечением») переносятся как есть: триггеры на время копирования выключены.
- Другие приюты старой базы и их волонтёры не переносятся; план показывает, сколько их осталось.

## Проверено

На локальном Supabase: старая схема с двумя приютами → `ops/backup/backup.sh` → `migrate.sh --apply` → новая схема. 17 сверок `PASS`; вход волонтёра со старым паролем и старым секретом TOTP проходит, запись с `aal2` работает, неверный пароль и волонтёр другого приюта отклоняются. Подробности в `docs/ASTRO-PORT-REPORT.md`.
