# Резервные копии

Каждую ночь GitHub Actions сохраняет базу и фото сайта в **отдельный приватный репозиторий**. Бесплатно.

| Что | Куда | Как часто |
|---|---|---|
| База: данные, схема, пользователи входа (почта и хэши паролей), политики доступа к фото | `db/ГГГГ-ММ-ДД.tar.gz.gpg`, зашифровано паролем копий | каждую ночь; в папке лежат последние 60 дней, более старые остаются в истории git |
| Фото из хранилища `pet-photos` | `photos/…`, как есть (фото и так публичные) | каждую ночь докачиваются только новые; **удалённые из хранилища фото в копии остаются** |

Почему не в этом репозитории: он публичный. В базе почта волонтёров, а журналы запусков публичного репозитория видны всем. Кроме того, GitHub отключает расписания в публичных репозиториях после 60 дней без активности.

Если запуск не удался, GitHub присылает письмо на почту владельца репозитория.

## Настройка (один раз, около 15 минут)

1. **Создайте приватный репозиторий**, например `a11y-shelter-backups`: GitHub → New repository → **Private**.
2. **Придумайте пароль копий**: длинный и случайный, лучше сгенерировать в менеджере паролей. Сохраните его **в двух местах**, например в менеджере паролей и на бумаге у доверенного человека в приюте.
   > ⚠️ Без этого пароля копии бесполезны: восстановить их не сможет никто, в том числе GitHub и Supabase.
3. **Возьмите строку подключения к базе**: Supabase → проект → кнопка **Connect** → **Session pooler**. Нужен именно pooler: у серверов GitHub нет IPv6, а прямое подключение к Supabase работает только по IPv6. Вместо `[YOUR-PASSWORD]` подставьте пароль базы.
4. **Добавьте секреты** в приватный репозиторий: Settings → Secrets and variables → Actions → New repository secret.
   - `SUPABASE_DB_URL` — строка из шага 3;
   - `SUPABASE_URL` — `https://<проект>.supabase.co` (Supabase → Project Settings → API);
   - `BACKUP_PASSPHRASE` — пароль из шага 2.

   Секреты вводятся только на сайте GitHub. Никуда их не пересылайте, в том числе в чат.
5. **Положите в приватный репозиторий файлы** из этой папки:
   - `backup.sh`, `restore.sh` и `restore-drill.sh` → в корень;
   - `backup.yml` → по пути `.github/workflows/backup.yml`;
   - `restore-drill.yml` → по пути `.github/workflows/restore-drill.yml`.
6. **Проверьте запуск**: Actions → backup → Run workflow. Через 1–3 минуты запуск должен стать зелёным, а в репозитории появятся папки `db/` и `photos/`.

## Еженедельная учебная тревога

По воскресеньям в 04:41 UTC (07:41 по Кишинёву) GitHub Actions (`restore-drill.yml`) запускает `restore-drill.sh`. Скрипт берёт **последнюю настоящую копию**, расшифровывает её секретом `BACKUP_PASSPHRASE`, поднимает одноразовый пустой Supabase на сервере GitHub, восстанавливает в него копию через `restore.sh` и сверяет результат с самой копией:

- в каждой таблице (пользователи входа, приюты, волонтёры, животные, нужды, проекты, галерея) столько же строк, сколько в копии;
- у всех пользователей сохранились пароли входа;
- политики хранилища на месте, значит, волонтёры смогут загружать фото;
- у анонимных посетителей нет прав на запись, вставка через API отклоняется;
- каждое фото из копии отдаётся байт в байт, основное фото каждого животного открывается.

Настоящий сайт и база в тревоге не участвуют. В журнал попадают только числа, без персональных данных. Если восстановление сломалось, запуск падает и GitHub присылает письмо, то есть вы узнаёте об этом в ту же неделю, а не в день беды.

Скрипт проверен на тестовой копии в трёх случаях: нормальная копия проходит; копия с неверным паролем и копия, из которой пропало фото животного, падают и называют причину.

## Восстановление

Восстанавливать нужно **в новый пустой проект Supabase**, не в старый.

1. Создайте новый проект Supabase (регион тот же, Франкфурт).
2. Склонируйте приватный репозиторий с копиями на компьютер, где есть `psql`, `gpg`, `curl` и `python3`.
3. Выполните:

   ```bash
   export TARGET_DB_URL='строка Session pooler нового проекта'
   export TARGET_URL='https://<новый-проект>.supabase.co'
   export TARGET_SERVICE_KEY='service_role ключ нового проекта'
   export BACKUP_PASSPHRASE='пароль копий'
   ./restore.sh db/2026-11-12.tar.gz.gpg photos
   ```

   Строка `Skipped role settings: … log_min_messages` — это нормально: служебная настройка Supabase, к проекту она не относится.

4. Переключите сайт на новый проект: замените `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY` и `SUPABASE_SERVICE_ROLE_KEY` в настройках хостинга. В Supabase → Authentication → URL Configuration укажите адрес сайта.
5. Адреса фото животных в базе указывают на старый проект. Замените их одним запросом в SQL Editor нового проекта:

   ```sql
   update public.pets
   set photo_url = replace(photo_url, 'https://<старый>.supabase.co', 'https://<новый>.supabase.co');
   ```

### Что восстановление делает и почему так

- Схема и данные восстанавливаются **одной транзакцией**: при любой ошибке не меняется ничего.
- Права доступа восстанавливаются **точно**. Новый проект Supabase по умолчанию даёт гостям полные права на новые таблицы, миграции проекта их отзывают, а дамп хранит только выданные права. Поэтому `restore.sh` перед восстановлением временно выключает права по умолчанию. Иначе после восстановления у анонимного посетителя оказались бы лишние права.
- Supabase сам обновляет свои служебные схемы (`auth`, `storage`), поэтому новый проект может оказаться старше или новее копии: служебной таблицы или колонки там может не быть. Данные сайта (`public`) восстанавливаются без изменений. В служебных схемах пустая недостающая таблица или колонка, пустая во всех строках, пропускается с предупреждением, а всё, что потеряло бы данные, останавливает восстановление с объяснением. Это нашла первая же тревога на настоящей копии: на боевом Supabase хранилище версии 1.89.13 с двумя новыми таблицами, а Supabase CLI 2.122.0 поднимает 1.84.19. Поэтому тревога поднимает хранилище той же версии, что на боевом проекте (секрет `SUPABASE_URL`).
- Загружаются только фото, которые были в хранилище в момент копии: их список берётся из самой копии базы (`storage.objects`). Папка `photos/` хранит и удалённые с сайта фото, на случай если их удалили по ошибке; их можно достать оттуда вручную. Если фото есть в списке, но его нет в `photos/`, восстановление останавливается с ошибкой и называет файл.
- Политики хранилища сохраняются отдельно (`storage_policies.sql`): Supabase CLI не включает их в дамп схемы. Без них волонтёры не смогли бы загружать фото.

### Проверено

Полный цикл «наполнить → скопировать → удалить базу и фото → восстановить» прогнан на локальном Supabase. Результат:
- приют, животное и волонтёр на месте, волонтёр входит со старым паролем;
- фото совпадают байт в байт;
- схема и права совпадают с миграциями;
- проходят все тесты базы из `supabase/tests`.

Еженедельная тревога восстанавливает копию в одноразовый Supabase. **Раз в квартал всё равно восстанавливайте копию вручную в настоящий новый проект Supabase**: так проверяется ещё и то, что инструкция понятна человеку.
